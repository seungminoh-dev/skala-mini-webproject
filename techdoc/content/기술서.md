판교캠퍼스 9반 P293 오승민

# 1. 서비스 개요

**프로젝트명**: 뚝딱 — 오피스 시설 민원 처리 서비스 (시스템명 FMS)

**한 줄 정의**: 오피스 빌딩 내 시설물 고장·불편 사항의 접수부터 처리 완료까지를 전산 기록으로 일원화하고, 축적된 처리 이력을 유지보수 의사결정의 근거로 활용하는 웹 서비스

## 1.1 대상 환경

> 본 기술서는 아래 가상 시나리오를 대상으로 설계한다.

| 구분 | 내용 |
| --- | --- |
| 대상 건물 | 판교 소재 오피스 빌딩 B동, 지상 8층 · 지하 2층(주차장·기계실) |
| 상주 인원 | 주간 기준 약 500명 |
| 관리 대상 설비 | 전기·조명 / 급배수·위생 / 공조(냉난방) / 승강기 / 출입·보안 / 집기·비품 (6개 카테고리) — 접수 단계에서는 신고자가 판단하지 못하는 경우를 위해 **기타·미분류**를 허용하고, 관리소장이 정정한다(FR-307) |
| 운영 인력 | 시설물 관리 소장 1명, 시설물 작업자 5명 (전기 1, 급배수·위생 2, 공조 1, 다목적 1) |
| 민원 발생량 | 주간 근무시간 기준 일 평균 15~20건 |

이 규모에서 민원 접수는 전화와 대면, 기록은 수기 대장과 담당자의 기억에 의존하고 있다. 작업자 5명이 8개 층·6개 설비 카테고리를 커버하는 동안 접수 창구는 관리실 한 곳뿐이어서, **접수 · 상태 공유 · 이력 축적** 세 지점이 모두 특정 개인의 가용성에 묶여 있다.

# 2. 현황 (As-Is)

| No | 액터 | 현황 |
| --- | --- | --- |
| AS-01 | 관리소장 | 자주 고장나는 설비의 정기 정비를 요청할 때 근거를 수기 대장이나 기억에 의존해야 하여, 명확한 수치를 제시할 수 없다 |
| AS-02 | 관리소장 | 현재 어떤 작업자가 어떤 업무를 보유 중인지 파악할 수 없어, 긴급 건을 누구에게 맡길지 판단할 근거가 없다 |
| AS-03 | 작업자 | 다음에 처리할 업무를 즉시 알 수 없어, 관리실에 전화해 묻거나 직접 현장에 가야 내용을 파악할 수 있다 |
| AS-04 | 작업자 | 동일 건에 대한 민원이 중복 접수되면 같은 업무가 여러 번 배정되어, 이미 처리한 건으로 재출동하는 낭비가 발생한다 |
| AS-05 | 사용자 | 어디로 신고해야 할지 몰라, 지나가는 작업자를 붙잡고 구두로 이야기해야 한다 |
| AS-06 | 사용자 | 관리실 전화번호를 알더라도 응대자가 부재중이면 접수 자체가 이루어지지 않는다 |

# 3. 원인 분석

수기와 기억에 의존하는 운영 방식은 세가지 측면에서 문제를 만든다.

- **C-1. 접수 채널이 사람에 의존한다** — 전화·대면이 유일한 접수 창구이므로, 응대자의 부재가 곧 접수 실패로 이어진다. (AS-05, AS-06)
- **C-2. 처리 상태가 기록되지 않아 공유되지 않는다** — 접수된 건의 현재 상태가 특정 개인의 기억에만 존재하여 다른 구성원이 조회할 수 없고, 중복 처리를 걸러낼 수 없다. (AS-02, AS-03, AS-04)
- **C-3. 처리 이력이 축적되지 않아 집계할 수 없다** — 완료된 건이 구조화된 형태로 남지 않아, 설비별 고장 빈도에 근거한 의사결정이 불가능하다. (AS-01)

# 4. 타겟 사용자 (액터)

| 액터 | 코드 | 정의 | 서비스에서의 목표 | 권한 경계 |
| --- | --- | --- | --- | --- |
| 시설물 관리 소장 | `ADMIN` | 건물 시설 운영을 총괄하는 책임자 (1명) | 전체 민원 현황을 파악해 지연 건을 조치하고, 축적된 이력으로 정비 계획을 수립한다 | 전체 민원 조회, 강제 배정·재배정·회수, 민원 분류 정보 수정, 반려, 통계 조회 |
| 시설물 작업자 | `WORKER` | 실제 수리·점검을 수행하는 시설 인력 (5명) | 처리할 업무를 스스로 확인해 가져가고, 처리 결과를 기록한다 | 미배정 민원 조회·선점, 본인 보유 민원의 반납 및 결과 등록 |
| 건물 사용자 | `USER` | 건물에 상주하며 시설을 이용하는 임직원 (약 500명) | 별도 가입 없이 즉시 신고하고, 신고의 처리 상황을 확인한다 | 민원 등록, 민원 조회(공개), 비밀번호 확인을 통한 본인 민원 수정·취소 |


## 4.1 인증 정책

| 액터 | 인증 방식 |
| --- | --- |
| `ADMIN` / `WORKER` | 사번·비밀번호 로그인 후 역할 기반 인가 |
| `USER` | **인증하지 않는다.** 민원 **열람은 공개**이며 민원 번호만으로 조회할 수 있다. 등록 시 입력한 4자리 비밀번호는 **수정·취소 시 본인 확인 용도로만** 사용한다 |

신고자에게 로그인을 요구하지 않는 이유는 C-1(접수 채널의 진입 장벽)을 해소하는 것이 본 서비스의 출발점이기 때문이다. 가입·로그인 절차는 그 자체로 새로운 접수 장벽이 된다. 열람까지 공개로 두는 것은, 조회 단계에서 본인 확인을 요구하면 "내 신고가 어떻게 처리되고 있는지"를 확인하려는 사용자에게 다시 장벽이 생기기 때문이다.

# 5. 핵심 가치

## 5.1 액터별 변화

- **`USER`** — 신고 창구를 찾아 헤매거나 응대자 부재로 접수가 누락되는 일이 **사라진다**. 가입 없이 즉시 신고할 수 있고, 신고한 민원의 처리 상태를 직접 **확인할 수 있게 된다**. (AS-05, AS-06 해소)
- **`WORKER`** — 다음 업무를 전화나 현장 방문으로 확인하던 과정이 **사라진다**. 중복으로 접수된 건이 반려로 정리되어 재출동이 **줄어든다**. (AS-03 해소, AS-04 완화)
- **`ADMIN`** — 작업자별 보유 업무와 지연 건을 한 화면에서 파악해 개입 시점을 **판단할 수 있게 된다**. 설비별 고장 이력이 수치로 축적되어 정기 정비 요청의 근거를 **제시할 수 있게 된다**. (AS-01, AS-02 해소)

## 5.2 핵심 가치 정의

본 서비스의 핵심 가치는 **특정 개인에 묶여 있던 시설 민원 처리 과정을 기록 기반으로 전환하는 것**이다. 접수는 응대자의 부재와 무관하게 이루어지고, 처리 상태는 관계자 모두에게 동일하게 보이며, 완료된 건은 사라지지 않고 이력으로 남아 다음 의사결정의 근거가 된다. 이후 기능의 채택 여부는 **"이 기능이 접수 누락 방지 · 상태 공유 · 이력 축적 중 무엇에 기여하는가"**를 기준으로 판단한다.

# 6. 운영 방식 결정 — 업무 배정 모델

**선점(Pull) 방식을 기본으로 하고, 관리소장의 강제 배정을 예외 경로로 운영한다.**

- **기본 경로** — 접수된 민원은 미배정 상태로 공용 목록에 노출되고, 작업자가 직접 선점한다. 이로써 AS-02의 "누구에게 배정할지 판단해야 하는 부담" 자체를 제거한다.
- **예외 경로** — 일정 시간 이상 아무도 선점하지 않은 건이나 긴급 우선순위 건에 대해, 관리소장이 특정 작업자에게 강제 배정한다.
- **전제 조건** — 예외 경로가 성립하려면 관리소장 화면에 **작업자별 현재 보유 건수 및 진행 상태**가 제공되어야 한다.

# 7. 설계 범위

## 7.1 포함

민원 등록·조회·수정·취소 / 미배정 민원 선점 및 반납 / 처리 결과 기록 / 관리소장의 강제 배정·재배정·회수 / 민원 분류 정보 수정 / 중복 및 대상 외 민원 반려 / 설비 카테고리별 집계 조회(단일 화면)

## 7.2 제외 (2차 범위)

| 제외 항목 | 근거 |
| --- | --- |
| 전체 공지(단수·정전 등) 발행 및 열람 | 민원 처리 흐름과 독립적인 별도 축이며, 상태 전이가 없어 본 설계의 핵심 가치에 기여하는 바가 작음 |
| 중복 민원 사전 탐지 및 동조 등록 | 유사 민원 판정 기준(동일 공간·카테고리·기간)의 정확도를 검증할 근거가 없는 상태에서 도입하면 정상 민원을 중복으로 오인할 위험이 있음. 사후 반려로 대체한다 |
| 정기 점검(예방 정비) 자동 스케줄링 | 사후 수리와 데이터 모델을 공유할 수 있으나, 점검 주기 산정 정책이 선행되어야 함 |
| 수리 비용·자재 정산 | 회계 도메인이 결합되어 범위가 과도하게 확장됨 |
| 외주 업체 계약 관리 | 본 설계의 액터가 내부 인력으로 한정됨 |
| 부품 재고 관리 | 민원 처리 흐름과 독립적인 별도 트랜잭션 축 |
| 외부 알림 채널(SMS·메신저) 연동 | 서비스 내 조회로 대체 가능하며, 외부 연동은 구현 단계 이슈 |
| 다건물·다사업장 확장 | 단일 건물로 한정해 문제 정의의 구체성을 확보 |

> 위 제외 항목과 근거는 12장의 제외 기능과 함께 최종 산출물의 **고려사항(다음 단계 개발 시 고려 사항)** 섹션으로 이관한다.

# 8. 설계 가정

- 본 문서의 수치(층수, 상주 인원, 작업자 구성, 일 평균 민원 건수)는 설계 검증을 위한 가정값이며 실측치가 아니다.
- `ADMIN` / `WORKER`의 인증 및 역할 기반 권한 체계는 존재하는 것으로 가정한다. 다만 과제 범위에 따라 API 명세에서 Security Schemes는 기술하지 않는다.
- `USER`의 민원 비밀번호는 인증 수단이 아니라 **본인 확인 수단**이므로, Security Schemes가 아닌 일반 요청 파라미터로 API 명세에 포함한다.
- 민원 내용에는 신고자를 식별할 수 있는 정보를 수집하지 않는다. 열람이 공개이기 때문이다.
- 설비 카테고리와 위치(층·공간) 정보는 서비스 구축 시점에 등록된 기준 데이터로 가정한다.
- **직원(`ADMIN`·`WORKER`) 계정은 서비스 구축 시점에 관리자가 등록한다.** 회원가입 절차를 두지 않는다 — 가입에는 승인 절차가 따르는데, 운영 인력이 고정된 단일 건물에서는 등록 시 사번·비밀번호를 지정하는 편이 단순하다.

# 9. 업무 처리 정책

## 9.1 민원 상태 정의

| 상태 | 코드 | 의미 |
| --- | --- | --- |
| 접수됨 | `RECEIVED` | 등록되었으나 담당 작업자가 정해지지 않은 상태. 미배정 목록에 노출된다 |
| 처리중 | `IN_PROGRESS` | 담당 작업자가 확정되어 조치가 진행 중인 상태 |
| 처리완료 | `COMPLETED` | 작업자가 조치 결과를 등록한 최종 상태 |
| 반려 | `REJECTED` | 중복 건이거나 관리 대상이 아니어서 처리하지 않는 상태 |
| 취소됨 | `CANCELED` | 신고자가 접수를 철회한 상태 |

> **설계 판단** — 담당자 확정(`ASSIGNED`)과 조치 착수(`IN_PROGRESS`)를 분리하지 않고 하나로 통합했다. 작업자가 민원을 가져가는 행위 자체가 곧 처리 시작이므로, 두 상태를 나누면 작업자에게 실익 없는 상태 변경 조작만 추가된다. 마찬가지로 신고자의 완료 확인 단계(`CLOSED`)를 두지 않고 작업자의 결과 등록을 최종 상태로 한다.

## 9.2 상태 전이

| 전이 | 수행 주체 | 조건 |
| --- | --- | --- |
| `RECEIVED` → `IN_PROGRESS` | `WORKER` (선점) | 담당 카테고리가 아닌 경우 경고 후 진행 가능 (P-01) |
| `RECEIVED` → `IN_PROGRESS` | `ADMIN` (강제 배정) | 작업자를 지정하여 배정 |
| `IN_PROGRESS` → `RECEIVED` | `WORKER` (반납) | 미배정 목록으로 복귀. 반납 사유(선택)를 처리 이력에 남긴다 |
| `IN_PROGRESS` → `RECEIVED` | `ADMIN` (회수) | 확인 절차를 거쳐 회수. 회수 사유(선택)를 처리 이력에 남긴다 |
| `IN_PROGRESS` → `IN_PROGRESS` | `ADMIN` (재배정) | 담당 작업자만 교체 |
| `IN_PROGRESS` → `COMPLETED` | `WORKER` (결과 등록) | 조치 내용 필수. 정형 조치 선택 1개 이상으로 충족되며 자유 서술은 선택이다 |
| `RECEIVED` → `CANCELED` | `USER` (취소) | 비밀번호 확인. 배정 전에만 가능 |
| `RECEIVED` / `IN_PROGRESS` → `REJECTED` | `ADMIN` (반려) | 사유 입력 필수. 중복 건은 원본 민원과 연결 |

민원 수정은 상태 전이를 일으키지 않는다. 신고자는 `RECEIVED` 상태에서만 신고 원문을 수정할 수 있고(FR-103), 관리소장은 상태와 무관하게 분류 정보를 수정할 수 있다(FR-307). 모든 상태 변경은 변경 주체·시각·사유와 함께 이력으로 기록되며, 이 이력이 민원 상세 화면의 타임라인과 통계의 원천이 된다.

## 9.3 선점 및 배정 정책

| No | 정책 | 내용 | 근거 |
| --- | --- | --- | --- |
| P-01 | 선점 자격 | 작업자는 카테고리와 무관하게 모든 미배정 민원을 선점할 수 있다. 다만 본인 담당 카테고리가 아닌 경우 **경고를 표시**한 뒤 진행 여부를 확인한다 | 신고자가 카테고리를 오분류한 민원이 관리소장의 정정 전까지 누구에게도 선점되지 못하고 방치되는 것을 방지한다 |
| P-02 | 지연 판정 | 우선순위별 선점 대기 시간이 임계값을 초과하면 해당 민원을 "지연"으로 표시한다 — **긴급 1시간 / 보통 6시간 / 낮음 24시간** | 강제 배정 개입 시점의 판단 기준 |

> **선점 경합** — 두 작업자가 동일 민원을 동시에 선점하려는 경우, 먼저 처리된 요청만 성공하고 나머지는 충돌로 거부된다. (API 명세에서 409 응답으로 정의)

> **동시 보유 상한을 두지 않는 이유** — 작업자 5명 규모에서 상한 정책은 관리 비용 대비 실익이 작고, 쏠림은 관리소장이 작업자별 보유 현황(FR-303)을 보고 재배정으로 조정할 수 있다. 상한 도입은 2차 범위로 둔다.

## 9.4 중복 민원 처리

| No | 정책 | 내용 |
| --- | --- | --- |
| D-01 | 사후 반려 | 현장 확인 또는 목록 검토 과정에서 중복이 발견된 경우, 관리소장이 해당 민원을 **원본 민원과 연결하여 반려**한다. 반려된 민원도 조회 가능하며, 신고자는 원본 민원의 진행 상황을 확인할 수 있다 |

> **사전 탐지를 두지 않는 이유** — 등록 시점에 유사 민원을 자동 제시하려면 "동일 공간 + 동일 카테고리 + 일정 기간"을 동일 건으로 판정해야 하는데, 이 기준의 정확도를 검증할 근거가 없다. 같은 층 화장실의 서로 다른 고장을 하나로 묶어버리면 실제 민원이 누락된다. MVP에서는 모든 신고를 접수하고, 중복은 처리 단계에서 사람이 판단해 정리한다.

**한 화면이 상태에 따라 역할을 바꾸는 경우**가 있다. W-03은 미배정이면 선점 판단 화면, 본인이 맡은 작업 중이면 작업 지시서, 완료되면 기록 열람이 된다. A-03도 상태에 따라 노출하는 행동과 본문 우선순위가 달라진다. 화면 ID를 상태별로 나누지 않고 하나로 두되, 상태별 행동은 13.4·13.5에서 표로 구분한다.

## 14.2 정규화 판단

위치(층·공간), 조치 결과, 반려 정보를 별도 테이블로 분리하지 않고 `complaint`에 인라인했다.

- **위치** — 층과 공간은 민원의 분류 속성일 뿐 독립적으로 조회·관리되는 대상이 아니며, 등록 화면의 두 드롭다운과 1:1로 대응한다.
- **조치 결과 · 반려 정보** — 각각 상태가 `COMPLETED` / `REJECTED`일 때만 채워지는 종결 정보다. "누가 언제 처리했는가"는 `complaint_history`가 이미 보관하므로, 본체에 `rejected_by` 같은 컬럼을 중복으로 둘 이유가 없다.

`complaint_history`는 이 서비스의 핵심 가치(이력 축적)를 담는 테이블이다. 민원 상세의 처리 이력 타임라인이 이 테이블을 그대로 렌더하고, 평균 처리 시간은 `REGISTER` ~ `COMPLETE` 간격으로 산출하며, 강제 배정 비율이 높은 카테고리는 정기 정비 요청의 근거가 된다. (AS-01)

# 15. API 설계

## 15.1 설계 규칙

1. **상태를 바꾸는 행위는 하위 리소스 조작으로 표현한다.** `POST /complaints/{id}/claim`, `DELETE /complaints/{id}/assignment` 처럼 전이의 의미를 경로와 메서드로 드러낸다. 본체에 대한 `PATCH`는 상태를 바꾸지 않는 내용 수정에만 쓴다.
2. **같은 리소스의 수정 경로를 권한별로 분리한다.** 신고자의 원문 수정과 관리소장의 분류 정보 수정은 수정 가능 필드와 허용 상태가 다르므로, 한 엔드포인트에서 역할로 분기하지 않고 경로를 나눈다.
3. **신고자의 본인 확인은 인증이 아니라 요청 파라미터다.** 조회는 공개이므로 비밀번호가 없고, 수정·취소 요청 본문에만 4자리 비밀번호를 담는다.
4. **목록은 직원 전용, 단건은 공개다.** 민원 번호를 아는 사람만 자기 민원을 볼 수 있어야 하므로 목록 조회와 단건 조회의 접근 범위를 다르게 둔다.

## 15.3 오류 응답

공통 응답으로 정의하고 `$ref`로 재사용한다.

| 코드 | 상황 |
| --- | --- |
| `400` | `INVALID_PAYLOAD`, `ORIGINAL_REQUIRED`, `INVALID_ORIGINAL` |
| `401` | `PASSWORD_MISMATCH`, `LOGIN_FAILED` |
| `403` | `FORBIDDEN` — 역할에 허용되지 않은 요청 |
| `404` | `COMPLAINT_NOT_FOUND`, `WORKER_NOT_FOUND` |
| `409` | `ALREADY_CLAIMED`, `NOT_EDITABLE`, `NOT_CANCELABLE`, `NOT_ASSIGNEE`, `INVALID_STATE` |

`409 ALREADY_CLAIMED`가 선점 경합(E-01)에, `409 NOT_EDITABLE` / `NOT_CANCELABLE`이 배정 후 수정·취소 제한(E-02)에 대응한다.

과제 범위에 따라 Security Schemes는 기술하지 않는다. 직원 전용 엔드포인트는 역할 기반 인가가 적용된다고 가정하고, 인가 실패 시의 응답만 정의했다.

# 16. 고려사항

## 16.1 해결한 설계 이슈

| 이슈 | 결정 | 근거 |
| --- | --- | --- |
| 수정·취소의 비밀번호 전달 | 취소를 `POST .../cancel`로 정의 | `DELETE` 요청 본문은 중간 프록시에서 보장되지 않는다. 취소가 물리 삭제도 아니다 |
| 동일 리소스의 두 수정 경로 | 경로 분리 | 수정 가능 필드와 허용 상태가 달라, 하나로 묶으면 요청 스키마가 조건부가 되어 명세가 흐려진다 |
| 열람 공개에 따른 번호 추측 | 비순차 식별자 `M-YYMMDD-XXXXXX` | 순차 증가값이면 인접 번호로 타인의 민원이 열린다. 혼동 문자(I·O·0·1)를 제외한 32자 집합을 쓴다 |
| 작업자 보유 현황의 표시 단위 | 보유 건수 + 현재 맡은 민원 | "진행 / 대기" 구분은 상태 모델에 `ASSIGNED`가 없어 만들 수 없다. 대신 지금 맡고 있는 민원을 보여 배정 판단 근거로 쓴다 |
| 배정 회수 사유의 전달 | `DELETE .../assignment?note=` 쿼리 | 회수는 배정이라는 하위 리소스의 삭제가 맞지만, `DELETE` 요청 본문은 보장되지 않는다. 선택 입력이므로 쿼리로 충분하다 |

## 16.2 남은 이슈

- **4자리 비밀번호의 강도** — 무차별 대입에 취약하므로 시도 횟수 제한이 필요하다. 접수 장벽을 낮추려는 설계 의도와 본인 확인 강도 사이의 절충점이다.
- **비인증 접수의 악용** — 허위·장난 신고에 대한 사전 통제 수단이 없다. 관리소장의 반려로 사후 대응하되, 반복 발생 시 접수 채널 제한을 검토한다.
- **중복 민원 사전 탐지** — 자동 판정 기준의 정확도를 검증할 근거가 없어 도입하지 않았다. 같은 층 화장실의 서로 다른 고장을 하나로 묶으면 실제 민원이 누락된다.

## 16.3 2차 범위로 미룬 기능

7.2와 12장에 정리한 제외 항목이 여기에 해당한다. 요약하면 전체 공지, 정기 점검 스케줄링, 비용·자재 정산, 외주 업체 관리, 부품 재고, 외부 알림 연동, 다건물 확장, 작업자 보유 상한, 신고자의 완료 확인·재요청, 기준 데이터 관리 화면이다.

여기에 다음 두 가지를 더한다.

| 항목 | 내용 | 미룬 이유 |
| --- | --- | --- |
| 직원 계정 관리 | 관리소장이 기사 계정을 등록·수정하는 화면. 등록 시 사번·비밀번호를 지정하는 방식이며 승인 절차는 두지 않는다 | 핵심 가치 3개에 직접 기여하지 않는다. 8장 가정대로 구축 시 등록으로 대신한다 |
| 장소 기준 데이터 분리 | 층·공간을 `category` 처럼 별도 테이블로 빼 동적 변경을 지원 | 새 건물 대응에는 유리하나 ERD·API·화면·기준 데이터가 함께 바뀐다. 단일 건물 MVP에서는 14.2의 인라인 설계로 충분하다 |

각 항목은 기능이 불필요해서가 아니라, **MVP의 핵심 가치(접수 누락 방지 · 상태 공유 · 이력 축적)에 직접 기여하지 않거나 선행 정책 정의가 필요해서** 제외했다.
