# USER FLOW 디자인 개편 기획서

> 오피스 시설 민원 처리 서비스 · 2026-09-16 · 구현 전달용
>
> 대상: 건물 사용자(USER)의 등록·조회·수정·취소 흐름.
> 이 문서는 개편할 화면과 동작을 정의한다. 문서 작성 시점에 애플리케이션 코드는 수정하지 않았다.

## 1. 개편 목적

사용자가 시설 문제를 접수하고, 발급받은 번호를 보관하고, 처리 상황을 다시 확인하는 흐름을 명확하게 만든다.

현재 화면은 네이비·오프화이트·얇은 구분선이라는 시각적 방향은 있으나, 화면별 정보의 우선순위와 다음 행동이 충분히 구분되지 않는다. 흰색 카드를 추가하거나 제거하는 것만으로는 해결하기 어렵다.

이번 개편은 다음 세 가지를 목표로 한다.

1. **입력하기 쉽다.** 무엇을 입력해야 하는지, 왜 진행할 수 없는지 바로 알 수 있다.
2. **다시 찾기 쉽다.** 접수번호와 조회 링크를 보관하고, 조회에 실패해도 즉시 다시 시도할 수 있다.
3. **현재 상황이 명확하다.** 접수 대기·작업 중·완료·반려·취소마다 다른 설명과 필요한 행동을 제공한다.

완성도는 카드 수나 장식의 양이 아니라, 각 화면에서 중요한 정보와 다음 행동이 분명한지로 판단한다.

## 2. 범위와 유지할 정책

### 2.1 개편 범위

| 화면 | 경로 또는 형태 | 개편 내용 |
| --- | --- | --- |
| U-01 사용자 홈 | `/` | 서비스 식별, 등록 진입, 번호 조회, 긴급 연락 안내 |
| U-02 민원 등록 | `/report` | 입력 묶음, 필수 항목, 검증, 사진 첨부 표시, 긴급도 안내 |
| U-03 접수 완료 | `/report/:id/done` | 접수증, 번호·조회 링크 복사, 처리 상황 이동 |
| U-04 민원 조회 | `/lookup` 및 홈 조회 영역 | 공통 조회 동작, 입력 보존, 실패 후 재시도 |
| U-05 민원 상세 | `/complaints/:id` | 상태별 정보 위계, 조치 결과, 원본 연결, 이력 |
| U-06 본인 확인 | 상세 화면의 대화상자 | 수정·취소 목적 구분, 오류 안내, 키보드 조작 |
| U-07 민원 수정 | `/complaints/:id/edit` | 등록 폼과 일관된 구성, 기존 내용·사진 편집 |
| USER 예외 상태 | 화면 내 안내 또는 대화상자 | 조회 실패, 통신 오류, 배정 경합, 최종 취소 확인 |

### 2.2 유지할 업무 정책

- USER는 회원가입이나 로그인을 하지 않는다.
- 민원 열람에는 민원 번호만 사용한다. 조회에 비밀번호를 요구하지 않는다.
- 등록 시 입력한 숫자 4자리 비밀번호는 수정·취소의 본인 확인에만 사용한다.
- 수정·취소는 현재 상태가 `RECEIVED`일 때만 가능하다. 과거 배정 여부를 임의로 새로운 제한 조건으로 만들지 않는다.
- 상태는 `RECEIVED`, `IN_PROGRESS`, `COMPLETED`, `REJECTED`, `CANCELED`의 5개를 유지한다.
- 담당자 확정과 작업 착수는 현재 설계상 같은 상태 전이다. 별도 `ASSIGNED` 단계나 사용자 완료 승인 단계를 추가하지 않는다.
- 민원 번호 `M-YYMMDD-XXXXXX` 형식과 기존 API·데이터 구조를 유지한다.
- 중복 민원은 사후 반려와 원본 연결로 처리한다. 등록 전 중복 검색·자동 판정은 추가하지 않는다.
- 기존 층·공간·설비·긴급도 기준값을 유지한다.
- 긴급도별 지연 기준은 관리 목적이다. 이를 사용자에게 약속한 출동·완료 시간으로 표시하지 않는다.
- 취소는 이력을 보존하는 상태 변경이다. 물리 삭제나 취소 복구 기능을 새로 만들지 않는다.

### 2.3 이번 개편에 포함하지 않는 것

- 시설기사·관리소장 화면 및 업무 흐름의 재설계.
- 회원가입, 마이페이지, 개인정보 수집, 비밀번호 재설정.
- 문자·메신저·푸시 알림, 처리 시간 예측, 실시간 채팅.
- 전체 민원 공개 목록, 자동 중복 탐지, 만족도 조사, 완료 승인.
- 최근 접수 내역의 자동 저장·복구 등 새로운 보관 정책.
- 실제 파일 저장 서버, 실제 API 연결, 운영 배포.
- 발표 자료·API 명세서·ERD의 자동 수정.

번호·조회 링크 복사, 입력 검증, 상태별 안내는 이번 개편에 포함한다. 위 제외 항목은 이를 구현하기 위한 전제 조건이 아니다.

### 3.2 문서·코드로 추가 확인한 항목

- `/lookup` 독립 조회 화면이 이미 존재한다. 홈과 같은 조회 규칙을 적용해야 한다.
- 취소는 비밀번호 확인 뒤 별도의 최종 취소 확인창을 거친다. 기존 2단계 구조를 유지한다.
- 사진은 현재 MOCK에서 파일명 중심으로 저장된다. 파일명을 실제 이미지 URL처럼 표시하면 안 된다.
- 수정 API는 사진 변경을 받지만 현재 수정 화면에는 사진 편집 UI가 없다. 기존 FR-103 범위 안에서 보완한다.
- 기존 기술서는 모바일 우선 반응형을 요구한다. 이번 브라우저 점검에서 모바일 동작을 검증한 것은 아니다.

사진 업로드, 최종 취소 실행, 수정 저장 도중 배정되는 경합 상황, 관리 대상 외 반려, 모바일은 이번 브라우저 점검에서 직접 실행하지 않았다. 아래 요구사항과 검수 항목은 개편 후 확인할 목표다.

## 4. 디자인 방향

### 4.1 화면의 성격

**홈과 등록은 시설 접수 창구, 완료와 상세는 접수증과 처리 기록으로 구성한다.**

- 홈: 어디에 접수하는지와 시작 방법을 빠르게 이해한다.
- 등록: 작성 순서와 필수 정보가 명확하다.
- 완료: 내가 접수한 건을 확인하고 조회 수단을 보관한다.
- 상세: 현재 상태와 처리 결과를 먼저 읽고, 필요할 때 원문과 이력을 확인한다.

장식용 대형 소개 영역, 균등한 카드 반복, 의미 없는 아이콘, 사용하지 않는 통계는 넣지 않는다. 흰색 면은 접수증·입력칸·대화상자처럼 내용이나 조작을 묶을 이유가 있을 때 사용한다.

### 4.2 공통 시각 기준

아래 수치는 개편의 설계 기준이며, 기존 화면에서 측정된 값이 아니다.

| 항목 | 기준 |
| --- | --- |
| 배경 | 기존 따뜻한 오프화이트 `#FAF9F7` 유지 |
| 주요 색 | 네이비 `#0F2854`, 보조색 `#1C4D8D`, `#4988C4`, `#BDE8F5` 유지 |
| 경고색 | `#B3401E` 유지. 입력 오류·긴급 안내·취소 확정 등 필요한 곳에만 사용 |
| 글꼴 | Pretendard. 번호·시각 등 식별 정보는 기존 모노스페이스 계열 활용 |
| 페이지 제목 | 데스크톱 28~32px, 모바일 24~28px |
| 본문·입력값 | 16px을 기본으로 설정 |
| 필드 라벨 | 14~15px, 일반 본문보다 약간 높은 굵기 |
| 보조 정보 | 13~14px. 필수 안내를 흐린 작은 글씨로 처리하지 않음 |
| 본문 행간 | 1.5~1.7 |
| 모서리·테두리 | 기본 radius 3px, 얇은 테두리. 카드 그림자와 한쪽 색 테두리 장식은 사용하지 않음 |
| 간격 | 8px 계열 사용. 필드 내부 8px, 항목 간 20~24px, 묶음 간 32~40px |
| 조작 영역 | 주요 버튼·입력 높이 44~48px을 기준으로 설정 |
| 상태 표현 | 짧은 텍스트와 채움 방식으로 구분. 색만으로 의미를 전달하지 않음 |

일반 라벨까지 모두 네이비로 강조하지 않는다. 페이지 제목·주요 행동·선택 상태에 네이비를 집중한다. 구분선은 정보 묶음의 경계를 나타내는 곳에만 둔다.

### 4.3 공통 레이아웃

- 헤더 다음 본문은 상단에서 시작한다. 화면 높이 또는 콘텐츠 길이에 따른 세로 중앙 정렬을 제거한다.
- 데스크톱의 본문 상단 여백은 기본 40px, 모바일은 24px로 통일한다.
- 데스크톱 공통 외곽 폭은 최대 1040px, 좌우 최소 여백 32px을 기준으로 한다.
- 등록·수정·완료·독립 조회의 실제 콘텐츠 폭은 최대 680px로 제한한다. 좁은 콘텐츠는 외곽 컨테이너 안에서 수평 중앙에 둘 수 있으나, 글과 제목은 좌측 정렬한다.
- 홈과 상세는 넓은 외곽 폭을 활용한다. 상세의 보조 열은 본문보다 좁게 둔다.
- 헤더에는 서비스·건물 식별, 처음으로, 직원 로그인을 유지한다. 직원 로그인은 USER의 주 행동보다 약하게 표현한다.
- 연락처는 클릭 가능한 전화 링크로 제공한다. 브라우저에 따라 통화 앱이 연결될 수 있으며 자동 발신하지 않는다.
- 푸터는 콘텐츠를 가리는 고정 오버레이로 만들지 않는다. 기존 연락처와 운영시간을 유지하되 문구를 과도하게 반복하지 않는다.
- 개발용 MOCK 역할 전환 영역은 제품 레이아웃의 일부로 다루지 않는다. 화면 검수 시 주요 조작 영역을 가리지 않게 한다.

## 5. 개편 후 사용자 흐름

### 5.1 신규 접수

`홈 → 민원 등록 → 접수증 확인 → 번호 또는 조회 링크 복사 → 처리 상황 보기`

복사는 선택 행동이다. 복사하지 않았다는 이유로 상세 이동을 막거나 별도의 동의 절차를 만들지 않는다.

### 5.2 기존 접수 조회

`홈 또는 /lookup → 번호 입력 → 조회 성공 시 상세`

`조회 실패 → 같은 입력 영역에서 번호 수정 → 다시 조회`

`저장한 상세 링크로 직접 진입 → 상세 또는 복구 가능한 오류 화면`

### 5.3 수정·취소

`접수 상태의 상세 → 민원 수정 → 비밀번호 확인 → 수정 폼 → 저장 → 상세`

`접수 상태의 상세 → 민원 취소 → 비밀번호 확인 → 최종 취소 확인 → 취소 상태의 상세`

비밀번호 확인 뒤 실제 저장·취소 시점에도 기존 API의 상태 검증을 따른다. 도중에 담당자가 배정되면 성공으로 표시하지 않고 최신 상태를 안내한다.

### 6.1 U-01 사용자 홈

**목적:** 시설 접수 창구임을 이해하고 등록 또는 조회를 바로 시작한다.

데스크톱 구성:

```text
공통 헤더

판교 오피스 B동
시설 민원 접수
시설 이용 중 불편한 점을 알려주세요.

새 민원을 등록하시나요?             접수한 민원을 확인하시나요?
위치와 증상을 남겨주세요.           민원 번호 [________________] [조회]
[민원 등록하기]                     비밀번호 없이 확인할 수 있습니다.
                                   오류가 있으면 입력 바로 아래 표시

긴급 상황 안내 · 긴급 직통 전화
공통 푸터
```

- 등록 영역은 네이비 주 버튼으로 시작점을 명시한다. 전체 영역을 거대한 버튼처럼 만들지 않는다.
- 등록과 조회를 동일 크기의 흰 카드 두 개로 감싸지 않는다. 여백과 필요할 경우 하나의 구분선으로 나눈다.
- 조회 영역은 입력과 조회 버튼이 하나의 조작 단위로 읽히게 한다.
- 긴급 안내는 홈에서 별도 스크롤 없이 발견할 수 있는 위치에 배치한다. 위험한 상황은 전화가 필요하다는 기존 취지를 유지한다.
- 관리실 연락처를 같은 본문 영역에 반복 나열하지 않는다.
- 모바일에서는 제목 → 등록 → 조회 → 긴급 안내 순서로 쌓는다. 긴급 안내가 지나치게 아래로 밀리면 제목 바로 아래로 올린다.

### 6.2 U-02 민원 등록

**목적:** 단일 페이지에서 필요한 정보를 빠짐없이 작성한다.

별도의 여러 단계 화면이나 진행률 표시를 추가하지 않는다. 아래 네 묶음을 간격과 짧은 제목으로 구분한다.

| 묶음 | 항목 | 요구사항 |
| --- | --- | --- |
| 위치와 설비 | 층, 공간, 설비 | 모두 필수. 층·공간은 충분한 폭에서 같은 줄에 표시 |
| 불편한 내용 | 한 줄 요약, 자세한 증상, 사진 | 요약·증상 필수, 사진 선택. 사진은 증상의 보조 자료로 배치 |
| 긴급도 | 긴급 / 보통 / 낮음 | 기본 보통. 선택 기준과 긴급 선택 안내 제공 |
| 수정·취소 확인 | 숫자 4자리 비밀번호 | 필수. 조회에는 쓰지 않는다는 점 명시 |

**입력 규칙**

- 상단에 `필수 항목을 입력해 주세요. 사진은 선택입니다.`를 표시하고, 필수 라벨에도 동일한 표식을 사용한다.
- 요약은 기존 60자 제한을 유지하고 현재 글자 수를 표시한다.
- 자세한 증상은 필수다. 임의로 선택 항목으로 바꾸지 않는다.
- 위치·설비의 기존 선택값을 유지한다. `기타·모름`을 찾기 쉽게 제공한다.
- 설비 도움말은 `잘 모르겠으면 기타·모름을 선택해 주세요.`처럼 짧게 작성한다.
- 비밀번호는 단일 입력칸으로 제공하며 숫자 키패드, 4자리 제한, 붙여넣기를 지원한다. 별도 로그인 비밀번호처럼 설명하지 않는다.
- 초기 화면부터 오류를 표시하지 않는다. 입력 후 해당 칸을 벗어났거나 제출을 시도했을 때 검증한다.
- 제출 버튼은 처리 중일 때 비활성화한다. 미입력 상태에서는 제출을 시도할 수 있고, 누락 항목 안내와 첫 오류 항목으로 이동하게 한다.
- 제출 실패 시 작성한 내용과 선택한 파일 목록을 유지한다.
- 중복 클릭으로 같은 민원을 여러 번 생성하지 않도록 처리 중 상태를 명확하게 표시한다.

**긴급도 안내**

| 선택 | 설명 문구 |
| --- | --- |
| 긴급 | 안전 위험이 있거나 피해가 빠르게 커지고 있어요. |
| 보통 | 시설 이용이 불편해 확인과 조치가 필요해요. |
| 낮음 | 이용은 가능하지만 점검이 필요해요. |

긴급 선택 시 다음 안내와 전화 링크를 선택 영역 바로 아래에 표시한다.

> 안전 위험이나 큰 피해가 우려되면 먼저 긴급 직통으로 연락해 주세요. 온라인 접수는 즉시 출동을 보장하지 않습니다.

기존 긴급 직통 번호를 사용한다. 긴급을 선택했다고 자동 발신하거나, 웹 접수를 막거나, 별도 승인을 요구하지 않는다.

**사진 처리**

- 파일을 선택하면 파일명 목록과 개별 제거 버튼을 표시한다.
- 수정 화면에서도 기존 목록 보존, 추가, 개별 제거를 지원한다.
- 현재 MOCK의 파일명 데이터와 실제 이미지 URL을 구분한다. 파일명만 있는 경우 깨진 이미지나 존재하지 않는 썸네일을 만들지 않는다.
- 이번 범위에서 실제 업로드 저장소를 구축하지 않는다. 사진 수·용량의 새로운 업무 제한을 근거 없이 추가하지 않는다.

**하단 행동**

- 주 버튼: `접수하기` / 처리 중 `접수 중…`.
- 보조 행동: `작성 취소`.
- 내용이 변경된 상태에서 취소·페이지 이동을 시도하면 작성 내용이 사라짐을 알리고 `계속 작성` / `나가기`를 제공한다. 아무것도 입력하지 않았다면 확인을 생략한다.

### 6.3 U-03 접수 완료

**목적:** 접수가 된 사실을 확인하고 이후 조회 수단을 보관한다.

```text
접수됐습니다
담당 기사가 배정되면 처리 상황에서 확인할 수 있습니다.

┌ 접수증: 평평한 흰색 면과 얇은 외곽선 ────────────┐
│ 민원 제목                                          │
│ 위치 · 설비 · 접수 시각                             │
│ 민원 번호                                          │
│ M-YYMMDD-XXXXXX                    [번호 복사]      │
│ [조회 링크 복사]                                   │
└────────────────────────────────────────────────────┘
다시 확인할 수 있도록 번호나 조회 링크를 보관해 주세요.

[처리 상황 보기]   처음으로
```

- 접수증은 흰색 면을 사용하는 대표 영역이다. 내부 정보를 다시 여러 카드로 쪼개지 않는다.
- 등록한 제목·위치·설비·접수 시각을 기존 데이터에서 가져온다. 새로고침해도 해당 번호의 접수증을 확인할 수 있어야 한다.
- 조회 링크는 완료 화면 주소가 아니라 `/complaints/:id`의 주소를 복사한다.
- 비밀번호를 번호나 링크에 포함하지 않는다.
- 번호 복사 성공 시 `민원 번호를 복사했습니다.`, 링크 복사 성공 시 `조회 링크를 복사했습니다.`를 표시한다.
- 클립보드 복사 실패 시 성공 메시지를 표시하지 않는다. 선택 가능한 번호 또는 링크와 수동 복사 안내를 제공한다.
- 분실 안내는 차분한 보조 문구로 표시한다. 강한 경고 상자가 완료 메시지를 압도하지 않게 한다.
- `처리 상황 보기`가 다음 화면으로 가는 주 행동이며, 복사는 접수증 안의 중요한 보조 행동이다.
- 존재하지 않는 완료 URL이나 조회 오류에는 거짓 성공 내용을 표시하지 않는다. 재시도 또는 번호 조회로 연결한다.

### 6.4 U-04 민원 조회

**목적:** 홈과 독립 조회 화면에서 동일한 방식으로 번호를 찾는다.

- 기존 `/lookup` 경로를 유지한다. 홈과 독립 조회 화면의 검증·오류·로딩 동작은 같아야 한다.
- 입력 라벨은 `민원 번호`, 예시는 `M-260915-A7K2Q9`처럼 형식을 보여준다.
- 앞뒤 공백은 제거하고 영문 소문자는 대문자로 정규화한다.
- 비어 있으면 `민원 번호를 입력해 주세요.`, 형식이 맞지 않으면 `민원 번호 형식을 확인해 주세요. 예: M-260915-A7K2Q9`를 표시한다.
- Enter와 조회 버튼 모두 같은 동작을 수행한다.
- 입력 화면에서 조회를 시작하면, 해당 번호를 확인한 뒤 성공한 경우에만 상세로 이동한다.
- 없는 번호는 입력을 보존하고 `해당 번호의 민원을 찾을 수 없습니다. 번호를 확인해 주세요.`를 입력 아래에 표시한다.
- 통신 오류는 없는 번호와 구분한다. `연결하지 못했습니다. 잠시 후 다시 시도해 주세요.`와 재시도를 제공한다.
- 번호를 잃어버린 경우 존재하지 않는 복구 기능이나 개인정보 입력 경로를 보여주지 않는다. 이름·연락처로 검색할 수 없다는 현재 정책을 짧게 설명한다.
- 독립 조회 화면에는 설계 의도나 내부 인증 구조를 설명하는 문장을 넣지 않는다. `민원 번호만 있으면 비밀번호 없이 확인할 수 있습니다.` 정도로 정리한다.

### 6.5 U-05 민원 상세

**목적:** 현재 처리 상황을 확인하고 필요한 경우 원문·결과·이력을 읽는다.

공통 순서:

1. 처음으로 이동하는 링크.
2. 짧은 상태명, 민원 제목, 현재 상황에 대한 한 문장.
3. 위치·설비·긴급도·접수번호·접수 시각.
4. 현재 상태에서 가장 중요한 결과 또는 안내.
5. 등록한 내용과 사진.
6. 처리 이력.

데스크톱에서 4~5는 넓은 본문 열, 6은 좁은 보조 열에 배치한다. 상태와 제목 영역은 두 열 위에 둔다. 모바일은 상태 → 결과·안내 → 원문 → 이력 순서로 쌓는다.

- 제목과 상태 설명을 하나의 긴 제목으로 합치지 않는다.
- 접수번호 옆에 복사, 보조 행동으로 조회 링크 복사를 제공한다. 완료 화면을 지나쳤어도 보관할 수 있어야 한다.
- 상태 정보 확인을 위한 `새로고침` 행동과 최근 확인 시각을 제공한다. 실제 자동 갱신이 없다면 자동으로 바뀐다고 약속하지 않는다.
- 최근 확인 시각은 화면이 데이터를 읽은 시각이다. 처리 이력의 변경 시각과 혼동하지 않게 표시한다.
- 새로고침 중에는 기존 내용을 유지하고 갱신 중임을 표시한다. 실패 시 기존 정보와 마지막 확인 시각을 남기고 재시도한다.
- 처리 이력은 발생 순으로 유지한다. 긴 이력은 최근 항목을 우선 노출하고 이전 이력을 펼쳐 볼 수 있다. 이력 데이터를 삭제하거나 새로운 사건을 만들어 표시하지 않는다.
- 없는 값에 임의의 담당자·예정 시각·조치 결과를 채우지 않는다.

**상태별 구성**

| 상태 | 대표 표현 | 우선 노출 | 가능한 행동 |
| --- | --- | --- | --- |
| `RECEIVED` | 접수 완료 | 담당 기사 배정을 기다리고 있다는 안내 | 민원 수정, 민원 취소, 번호·링크 복사, 새로고침 |
| `IN_PROGRESS` | 작업 중 | 담당 기사와 현재 상황, 등록한 내용 | 번호·링크 복사, 새로고침, 관리실 전화 |
| `COMPLETED` | 처리 완료 | 조치 내용, 완료 시각, 실제 데이터에 있는 소요 시간·조치 사진 | 번호·링크 복사, 처음으로 |
| `REJECTED` + 중복 | 중복 접수 | 원본 민원의 제목·현재 상태·연결 | 기존 민원 처리 상황 보기 |
| `REJECTED` + 기타 사유 | 접수 반려 | 실제 사유와 설명 | 사유에 맞는 관리실 문의 또는 새 민원 등록 |
| `CANCELED` | 접수 취소 | 취소 시각과 접수가 철회됐다는 설명 | 새 민원 등록, 처음으로 |

세부 기준:

- 접수 상태의 수정·취소 버튼은 제목 주변에 묶는다. 취소를 수정과 동일한 주 버튼으로 강조하지 않는다.
- 작업 중 상태의 수정 제한은 필요한 위치에 보조 문장으로 안내한다. 화면 전체에서 가장 강한 경고 상자로 만들지 않는다.
- 작업 중 추가 사항 안내는 `추가로 전달할 내용은 관리실에 문의해 주세요.`와 기존 관리실 전화로 연결한다. 동일 민원을 새로 접수하도록 기본 유도하지 않는다.
- 완료 상태에서는 조치 결과가 원문보다 먼저 읽히게 한다. 배정 이후 수정 불가 경고는 반복 표시하지 않는다.
- 중복 반려는 `같은 문제가 이미 접수되어 있습니다. 기존 민원에서 처리 상황을 확인해 주세요.`로 안내한다.
- 원본이 완료됐다면 `처리 중`이라고 쓰지 않는다. 연결된 원본의 실제 상태를 표시한다.
- 관리 대상 외, 내용 확인 불가 등 반려 사유는 실제 데이터에 맞춰 표현한다. 모든 반려에 같은 문장이나 같은 행동을 강제하지 않는다.
- 원본 연결 정보가 없거나 조회되지 않으면 거짓 링크·상태를 표시하지 않고 연결 불가 안내와 관리실 문의를 제공한다.
- 취소 상태에 담당자 배정 제한 안내를 표시하지 않는다.
- 공유 링크로 상세에 직접 진입했는데 번호가 없으면 입력값이 채워진 조회 영역과 처음으로 이동을 제공한다. 오류 문장만 남기지 않는다.

### 6.6 U-06 본인 확인과 최종 취소 확인

**비밀번호 확인창**

- 수정 제목: `민원을 수정하려면 비밀번호를 입력해 주세요`.
- 취소 제목: `민원을 취소하려면 비밀번호를 입력해 주세요`.
- 설명: `접수할 때 정한 숫자 4자리를 입력해 주세요.`
- 단일 입력칸, `닫기`, `확인`으로 구성한다. 확인을 로그인으로 표현하지 않는다.
- 잘못된 비밀번호는 입력 아래에서 안내하며 같은 창에서 다시 시도한다.
- 현재 상태가 달라져 수정·취소할 수 없다면 비밀번호 오류와 구분하고 최신 상세로 돌아가게 한다.

**대화상자 공통 조작**

- 열리면 입력칸으로 초점을 이동한다.
- Tab과 Shift+Tab은 열린 창 내부에서만 이동한다.
- 배경 버튼과 입력은 조작되지 않아야 한다.
- Esc 또는 닫기로 창을 닫으면 원래 열었던 버튼으로 초점을 돌린다.
- 비밀번호 입력에서 Enter는 본인 확인만 수행한다. 취소 흐름의 최종 확정까지 연속 실행되지 않게 한다.
- 창의 제목·설명과 오류 메시지를 보조기술에서도 인식할 수 있게 연결한다.

**최종 취소 확인창**

- 기존처럼 비밀번호 확인을 통과한 뒤 별도의 확인창을 연다.
- 제목: `이 민원을 취소할까요?`
- 민원 제목과 위치를 함께 표시해 취소 대상을 확인할 수 있게 한다.
- 설명: `취소한 접수는 되돌릴 수 없습니다. 다시 접수하려면 새 민원을 등록해 주세요.`
- 버튼: `그대로 두기` / `민원 취소`.
- 취소 버튼에만 경고색을 사용한다. 초기 초점은 `그대로 두기`에 둔다.
- 처리 중에는 중복 확정을 막고 완료 후 같은 민원의 취소 상태 상세를 표시한다.
- 실패 시 취소됐다고 표시하지 않는다. 배정 경합이면 최신 상태, 통신 오류면 재시도를 안내한다.

### 6.7 U-07 민원 수정

**목적:** 이미 등록한 정보를 익숙한 폼에서 수정한다.

- 등록 화면의 항목 순서·라벨·간격·검증을 재사용한다.
- 비밀번호를 새로 정하는 입력은 넣지 않는다. 본인 확인을 통과한 상태를 사용한다.
- 기존 제목·내용·위치·설비·긴급도·사진을 모두 보존해 불러온다.
- 기존 API에서 허용하는 항목만 수정한다. 상태·담당자·조치 결과는 수정 대상이 아니다.
- 사진 목록과 추가·제거 기능을 제공하되 MOCK의 파일명 저장 한계를 지킨다.
- 주 버튼은 `수정 완료`, 보조 행동은 `수정 취소`로 통일한다.
- 변경 후 저장하지 않고 나가면 `계속 수정` / `저장하지 않고 나가기`를 제공한다.
- 저장 성공 시 상세로 돌아가 `수정했습니다.`를 표시하고 갱신된 내용과 이력을 확인할 수 있게 한다.
- 저장 도중 담당자가 배정되어 거절되면 이유를 알린다. 작성 내용을 즉시 비우지 않고 최신 상세로 돌아갈 행동을 제공한다.
- 본인 확인 상태가 없는 직접 진입·새로고침에서는 상세로 돌려보내고 `수정하려면 비밀번호를 다시 확인해 주세요.`라고 안내한다.

## 7. 반응형과 접근성

다음은 구현 후 확인해야 할 기준이다. 현재 모바일 화면의 검증 결과가 아니다.

| 화면 폭 | 구성 기준 |
| --- | --- |
| 1024px 이상 | 넓은 홈, 상세 본문·이력 2열. 폼과 접수증은 좁은 폭 유지 |
| 768~1023px | 충분한 읽기 폭이 확보되는 범위에서 2열 사용. 공간이 부족하면 1열 전환 |
| 767px 이하 | 본문 1열, 좌우 20px 내외 여백, 긴 제목·번호·버튼 줄바꿈 처리 |

- 360px, 390px, 768px, 1280px, 1920px에서 검수한다.
- 가로 스크롤 없이 본문·번호·폼·대화상자를 읽고 조작할 수 있어야 한다.
- 긴 한글 제목, 긴 민원 번호, 두세 문장의 본문, 긴 처리 이력을 포함해 확인한다. `123` 같은 짧은 테스트 내용만으로 밀도를 결정하지 않는다.
- 키보드가 열려도 현재 입력칸과 오류 메시지를 확인할 수 있어야 한다.
- 버튼을 고정 배치하는 경우 콘텐츠를 가리지 않아야 한다. 본 기획의 기본은 흐름 안의 버튼이며 모바일 하단 고정 바는 필수 요소가 아니다.
- 모든 입력에 실제 라벨을 연결한다. 층·공간처럼 나란한 입력도 각각 식별할 수 있어야 한다.
- 긴급도는 그룹 이름과 현재 선택 상태를 전달한다.
- 주요 행동에는 명확한 초점 표시를 제공한다.
- 오류는 색상과 문장을 함께 사용한다. 복사·저장 성공 메시지도 화면과 보조기술에서 확인할 수 있게 한다.

### 9.2 개발자에게 전달할 경계

- 주 변경 대상은 `src/views/user/`와 USER 전용 스타일이다.
- `PubShell.vue`는 직원 로그인에서도 사용될 수 있으므로 적용 범위를 확인한다.
- `AppDialog.vue`와 공통 스타일을 변경하면 다른 역할의 화면에도 영향이 갈 수 있다. USER 전용 구성 또는 명시적인 변형을 사용하고 공유 부분은 회귀 확인한다.
- `src/mock/api.js`의 등록·조회·본인 확인·수정·취소 계약을 유지한다. 시각 개편을 위해 상태 전이 규칙을 바꾸지 않는다.
- 기존 작업 중 변경을 덮어쓰거나 프로젝트 전체 스타일을 일괄 교체하지 않는다.
- 기존 기술서의 업무 정책과 팔레트는 유지한다. 이번 문서의 새로운 레이아웃은 USER 화면에 적용하며 직원 화면의 레일·테이블 구성을 USER에 강제로 적용하지 않는다.
- 폼, 조회 입력, 접수번호 복사, 상태 요약, 대화상자는 반복 사용되는 동작과 표현이 일치하도록 구성한다. 구체적인 컴포넌트 분할은 구현자가 결정한다.
- 실제 업로드·알림·새 인증 체계를 구현해야만 이 개편이 끝나는 구조로 만들지 않는다.

- [ ] 취소는 비밀번호 확인과 최종 대상 확인을 모두 거친다.
- [ ] 취소 실패를 성공으로 표시하지 않는다.
- [ ] 취소된 민원은 취소 상태와 이력을 유지한다.

### 10.3 조작·화면
