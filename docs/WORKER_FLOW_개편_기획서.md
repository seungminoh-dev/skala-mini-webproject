>
> 대상: 시설기사(WORKER)의 미배정 목록 → 선점 → 처리 결과 등록 → 반납 흐름.
> 근거: ① 내장 브라우저로 FR-201~206 직접 조작 검증(3.1) ② 화면 캡처 검수(3.2) ③ 승민 검증 노트 `docs/WORKER-FLOW-ROW.md`(12장에서 항목별 종합).
> 이 문서는 개편할 화면과 동작을 정의한다. 문서 작성 시점에 WORKER 화면 코드는 수정하지 않았다.

## 1. 개편 목적

기사가 **다음에 할 일을 고르고, 현장에 가서, 결과를 남기는** 세 동작이 끊기지 않게 만든다.

USER 흐름 개편(`docs/USER_FLOW_개편_기획서.md`)으로 신고자 화면은 정리됐지만, 기사 화면은 "레일 + 전폭 테이블"이라는 골격만 있고 그 안의 정보 우선순위와 다음 행동이 기사 관점으로 배치되지 않았다. 특히 **결과를 남기는 화면에서 신고 원문을 볼 수 없고**, **내 작업에서 상세로 들어갈 길이 없으며**, 목록·상세 모두 **정보 위계가 없어 무엇을 먼저 봐야 하는지 화면이 말해주지 않는다**.

이번 개편의 목표:

1. **고르기 쉽다.** 어디(층·공간)·무엇(설비)·얼마나 급한가가 목록에서 한눈에 읽히고, 기사가 정렬 기준을 고를 수 있다.
2. **현장에서 쓸 수 있다.** 맡은 작업의 원문·위치·사진을 결과 입력 화면에서 바로 본다. 결과 입력은 바쁜 현장에서 몇 초 안에 끝난다.
3. **기록이 남는다.** 선점·반납·완료가 피드백과 함께 이력에 정확히 남고, 완료한 건을 다시 볼 수 있다.

완성도는 화면 수나 장식이 아니라, 기사가 화면을 오가지 않고도 한 건을 끝까지 처리할 수 있는지로 판단한다.

## 2. 범위와 유지할 정책

### 2.1 개편 범위

| 화면 | 경로 | 개편 내용 |
| --- | --- | --- |
| W-02 미배정 민원 (현 "대기 중인 작업") | `/worker` | 열 구성·열 폭·정렬 선택·필터 우선순위·빈 상태·용어 |
| W-03 민원 상세 | `/worker/complaints/:id` | 메타 위계, 첨부 사진 표시, 담당 외 안내 단일화, 관련 작업 문구, **작업 중·완료 상태의 열람 역할 추가**, PC 폭 상한 |
| W-04 담당 외 경고 | 상세의 대화상자 | 문구 간결화, 상세 안내와 중복 제거 |
| W-05 내 작업 | `/worker/tasks` | 행 → 상세 진입, 탭별 열 구성, 열 폭, 경과 시간, 버튼 줄바꿈 |
| W-06 처리 결과 등록 | `/worker/complaints/:id/complete` | 원문 컨텍스트 병기, 하단 행동, 입력 부담 축소(7장 결정), 사진 목록 |
| E-01 선점 충돌 | 상세의 대화상자 | 문구 확인, 목록 복귀 |
| E-04 반납 확인 | 결과 화면의 대화상자 | 용어, 반납 메모(7장 결정) |
| 공통 셸 | `StaffShell.vue` | 레일 프로필에 담당 설비, 행동 피드백, 내용 폭 상한, 모바일 레일 |

W-01 직원 로그인은 이미 개편했다(사내 시스템형). ADMIN 화면은 별도 기획(ADMIN-FLOW)에서 다룬다.

### 2.2 유지할 업무 정책 (기술서 기준 — 바꾸지 않는다)

- 선점(Pull) 기본. 미배정 민원은 `RECEIVED` 상태로 공용 목록에 노출되고 기사가 직접 맡는다. (6장)
- **P-01** 담당 외 설비도 선점할 수 있다. 경고 후 진행. 담당 외 선점은 이력 note `담당 외 설비`로 남는다. (9.3)
- **P-02** 지연 판정 긴급 1시간 / 보통 6시간 / 낮음 24시간. 관리소장 개입 기준이며 기사에게 표시는 하되 약속 시간처럼 쓰지 않는다. (9.3)
- 선점 경합은 먼저 도달한 요청만 성공, 나머지는 `409 ALREADY_CLAIMED`. (9.3, E-01)
- 상태 5개. 선점 = `RECEIVED → IN_PROGRESS`, 반납 = `IN_PROGRESS → RECEIVED`, 완료 = `IN_PROGRESS → COMPLETED`. `ASSIGNED` 단계를 만들지 않는다. (9.1, 9.2)
- 동시 보유 상한 없음. (9.3)
- **기본 정렬**은 긴급도 → 경과 시간(오래된 순). 기사가 다른 정렬을 고르는 것은 표시 계층에서만 한다(API 정렬 불변). (FR-201, 12장 R-01)
- **용어는 기술서를 기준으로 화면을 맞춘다.** 화면 표기가 기술서와 다르면 기술서 쪽으로 통일한다. (USER 개편에서 확정한 원칙, 12장 R-02·R-05)
- 디자인 규칙: 좌측 네이비 레일 + 전폭 테이블, 헤어라인·면 분할, 8px 사각 인디케이터, radius 3px, 경고색 `#B3401E` 하나, 상태는 채움 방식으로 구분. 카드+그림자·알약 태그·한쪽 색 테두리 금지.

**결정 후 바뀔 수 있는 정책** (7장): 완료 시 조치 내용 필수 여부(P-H), 소요 시간 입력 여부(P-G), 반납 사유 기록(P-A). 이 셋은 기술서 9.2·FR-205·ERD·API에 닿으므로 승민 결정 후에만 반영한다.

### 2.3 이번 개편에 포함하지 않는 것

- 관리소장 화면·업무 흐름의 재설계 (ADMIN-FLOW 별도).
- 실시간 갱신·푸시 알림. 수동 새로고침을 유지한다.
- 기사 간 작업 이관(A→B 직접 넘기기). 반납 → 재선점 또는 관리소장 재배정만 존재한다.
- 작업 순서 최적화·경로 추천·근무 일정.
- 실제 파일 저장소, 실제 API, 운영 배포.
- 발표 자료·API 명세서·ERD의 자동 수정. 7장 결정에 따른 명세 변경은 별도 승인 후 반영한다.

## 4. 디자인 방향

### 4.1 화면의 성격

**미배정 목록은 작업판, 상세는 작업 지시서, 결과 화면은 작업 일지다.**

- 미배정 목록: 어디·무엇·얼마나 급한가를 훑고 고른다. 훑는 기준(정렬)은 기사가 정한다.
- 상세: 현장에 가기 전에 알아야 할 것(원문·사진·같은 위치 작업)을 읽고 맡을지 결정한다. 맡은 뒤에는 같은 화면이 작업 지시서가 되고, 끝난 뒤에는 기록이 된다.
- 결과: 지시서를 옆에 두고 일지를 쓴다. 쓰는 데 몇 초면 된다.

"AI틱함"을 빼는 기준 — 다음은 쓰지 않는다: 균등 분할 흰 박스 그리드, 상황과 무관하게 항상 보이는 안내 문장, 헤더 우상단에 고정된 폼 제출 버튼, 데이터가 적을 때 빈 공간을 채우려는 장식 위젯, 화면 폭에 맞춰 늘어나기만 하는 2열, 모든 값이 같은 회색·같은 크기인 부제.

### 4.2 공통 시각 기준

직원 콘솔 토큰(`src/styles/main.css`)을 유지한다. 신고자 화면과 달리 본문 14px 밀도를 지킨다 — 콘솔은 훑는 화면이다.

| 항목 | 기준 |
| --- | --- |
| 골격 | 좌측 네이비 레일 224px + 작업 영역. 모바일(≤900px)은 레일이 상단 탭 |
| 내용 폭 | **테이블은 전폭. 상세·폼은 최대 1100px**(본문 열 최대 720px, 보조 열 320px) — WX-26 |
| 테이블 열 | 요청 내용 열 최대 480px. 값이 짧은 열(긴급도·설비·접수)은 내용 폭으로 고정. 남는 폭은 오른쪽 여백 — WX-25 |
| 위계 | 한 행 안에서 **위치·제목 = 본문색 굵게**, **번호·경과 = 모노 회색 작게**. 같은 회색·같은 크기의 값을 나란히 두지 않는다 — WX-01 |
| 페이지 제목 | 21px. 서브타이틀은 **상태·건수 같은 사실**만 (설명문 금지) |
| 상태·지연 | 8px 사각 인디케이터. 지연만 경고색. 긴급도 `긴급`만 경고색 텍스트 |
| 폼 | 라벨 12.5px 굵게, 필수 표식 `*`, 오류는 항목 아래 경고색 문장. 입력 높이 40px. **탭 한 번으로 채우는 선택지는 사각 토글(`.ftog`)** |
| 행동 | 목록·상세 헤더의 행동은 유지. **폼 제출은 폼 하단**. 주 버튼 네이비 단색 1개, 나머지 외곽선 |
| 피드백 | 이동 후 상단 `note` 한 줄. 토스트·애니메이션 없음 |

### 4.3 공통 레이아웃

- 레일 프로필: 이름 · 직함 · 담당 설비. 로그아웃.
- 페이지 헤더: 제목 + 사실 서브타이틀 + (목록·상세의) 행동 버튼. 결과 폼은 헤더에 제목만.
- 상세·결과는 2열(본문 : 보조 = 720 : 320, 최대 1100px). 모바일은 1열.
- 데이터가 적어도 빈 공간을 억지로 채우지 않는다. 대신 캡처·시연은 현실적인 시드로 한다.

## 5. 개편 후 사용자 흐름

### 5.1 선점

`미배정 민원 → (정렬·필터 조정) → 행 클릭(상세) → 원문·사진·같은 위치 작업 확인 → 이 작업 맡기 → (담당 외면 확인 한 번) → 내 작업(안내: "맡았습니다")`

충돌(`409`)이면 "다른 기사가 먼저 맡았습니다" → 목록 새로 불러오기.

### 5.2 처리

`내 작업 → 행 클릭(상세, 작업 중) → 처리 결과 남기기 → 원문을 옆에 두고 조치 선택(+메모·사진) → 작업 완료 → 내 작업 완료 탭(안내: "처리 결과를 남겼습니다") → 완료 행 클릭으로 언제든 다시 열람`

### 5.3 반납

`상세(작업 중) 또는 결과 화면 → 반납 → 확인(메모 선택, P-A) → 미배정 민원(안내: "미배정 목록으로 돌려보냈습니다")`

## 6. 화면별 상세 기획

### 6.1 W-02 미배정 민원

**목적:** 다음에 할 일을 고른다. 고르는 기준은 기사가 정한다.

```text
미배정 민원                                              [새로고침]
담당자 미배정 민원 N건 · 지연 M건

[내 담당] [전체] [전기·조명] [급배수·위생] … [기타·모름]      정렬: [긴급한 순] [오래된 순] [위치 순]

긴급도      위치         요청 내용                      설비        접수
긴급 ■지연   7층 회의실   냉방 작동 안 함                 공조        1시간 18분 전
                       M-260915-C9M4T7
보통        2층 탕비실   싱크대 배수 불량                급배수·위생  30분 전
                       M-260915-N9W4B7
                                              ← 요청 내용 열 최대 480px, 나머지는 왼쪽으로 붙는다
```

- 열 순서: 긴급도(+지연 마커) → 위치(굵게) → 요청 내용(제목 굵게, 번호는 모노 회색 부제) → 설비 → 접수 경과. 상태 열은 없앤다(WX-01~03).
- **정렬 선택**(WX-27): `긴급한 순`(기본 = API 정렬 그대로) / `오래된 순`(createdAt 오름차순) / `위치 순`(층 오름차순 → 공간). 표시 계층에서만 정렬하고 API 호출은 바꾸지 않는다. 선택은 세션 동안 유지(`sessionStorage`).
- 필터: `내 담당`을 첫 탭으로. 기본 선택은 P-D. 결정 전 기본은 `전체`.
- 필터 빈 상태: `급배수·위생에 미배정 민원이 없습니다.` + `전체 보기` 버튼(WX-05). 전체가 비면 `미배정 민원이 없습니다.`
- 행 전체 클릭 → 상세. 행 hover 면으로 클릭 가능성을 드러낸다.
- 담당 표식 `·`와 범례는 레일 프로필로 대체되면 제거한다(WX-20).
- 용어(P-F 채택 시): 페이지 제목·레일 메뉴 `미배정 민원`, 서브타이틀 `담당자 미배정 민원 N건`.

### 6.2 W-03 민원 상세 (+ W-04, E-01)

**목적:** 맡을지 판단한다. 맡은 뒤에는 작업 지시서, 끝난 뒤에는 기록이다.

공통 순서 (내용 폭 최대 1100px, WX-26):

1. 돌아가는 링크 (`← 미배정 민원` 또는 `← 내 작업`, 진입 경로 기준)
2. 상태 인디케이터 + 지연 마커, **민원 제목(굵게, 가장 크게)**
3. 한 줄 메타: **`7층 회의실` · 공조 · 긴급** · 1시간 18분 전 접수 · `M-260915-C9M4T7`(모노 회색) — 4칸 그리드 폐기(WX-06). 위치는 굵게.
4. (담당 외일 때) 사실 안내 한 줄: `공조 담당은 이상철 · 정민수입니다. 내 담당이 아니어도 맡을 수 있습니다.`
5. 본문 열: 신고 내용 → 첨부 사진(파일명 목록, 없으면 `첨부 사진 없음`) → 같은 위치에서 진행 중인 작업(있을 때만) → (완료 상태) 조치 결과
6. 보조 열: 처리 이력

**상태별 행동 (헤더 우측)**

| 상태 | 행동 | 본문 우선 |
| --- | --- | --- |
| `RECEIVED` | `이 작업 맡기` (주) | 신고 내용 |
| `IN_PROGRESS` · 담당 본인 | `처리 결과 남기기` (주) · `반납` (보조) | 신고 내용 |
| `IN_PROGRESS` · 담당 타인 | 행동 없음. 메타에 `담당 {이름} 시설기사` | 신고 내용 |
| `COMPLETED` | 행동 없음 | **조치 결과가 신고 내용보다 먼저** (WX-14) |
| 그 외 | 행동 없음 | 신고 내용 |

**같은 위치에서 진행 중인 작업** (WX-09)

- 담당자가 본인: 행 우측 `내가 맡고 있음`. 경고 문구 없음.
- 담당자가 타인: 행 우측 담당자 이름. 상단 한 줄 `같은 자리에 다른 작업이 잡혀 있습니다. 같은 건이면 관리소장에게 알려 정리하세요.`
- 담당자 없음(대기): 행 우측 `담당자 없음`.
- 섹션이 비면 렌더하지 않는다. 헤더 서브타이틀의 상시 안내 문장은 삭제한다(WX-10).

**W-04 담당 외 확인** (WX-08)

- 제목: `내 담당 설비가 아닙니다`
- 설명: `맡으면 내 작업 목록으로 들어옵니다. 이력에 담당 외 선점으로 기록됩니다.`
- 버튼: `돌아가기` / `맡기`. 초점은 `맡기`.

**E-01 선점 충돌**

- 제목 `다른 기사가 먼저 맡았습니다`, 설명 `거의 동시에 같은 작업을 선택했습니다. 목록을 새로 불러옵니다.` 유지.
- 버튼 `목록으로` 하나. Esc·배경 클릭도 목록으로.

### 6.3 W-05 내 작업

**목적:** 내가 맡은 것과 끝낸 것을 본다. 끝낸 것도 다시 볼 수 있다.

- 탭: `작업 중` / `완료`. 서브타이틀은 현재 탭 건수 (`작업 중 2건`).
- 작업 중 열: 긴급도 → 위치(굵게) → 요청 내용(최대 480px) → 설비 → 맡은 지(assignedAt 경과, WX-15) → `결과 남기기`(WX-13).
- 완료 열: 위치 → 요청 내용 → 설비 → 완료 시각 → 조치 요약(조치 내용 첫 줄, 없으면 `작업 완료`) (WX-14).
- 행 클릭 → 상세(작업 중은 지시서 모드, 완료는 열람 모드)(WX-11·12).
- 정렬: 작업 중은 맡은 순(오래된 것 위), 완료는 최근 완료 순. 현재 API 정렬(assignedAt 내림차순)을 작업 중 탭에서 뒤집는다 — 오래 붙잡은 것이 위로.
- 빈 상태: `맡은 작업이 없습니다. 미배정 민원에서 골라보세요.` + 링크.

### 6.4 W-06 처리 결과 등록 (+ E-04)

**목적:** 지시서를 옆에 두고 일지를 쓴다. 현장에서 몇 초 안에 끝난다.

```text
처리 결과 남기기
■ 작업 중  6층 화장실 세면대 누수 · 6층 화장실 · M-260915-A7K2Q9

┌ 본문 열 (최대 720px) ───────────────────┐  ┌ 보조 열 (320px) ────────┐
│ 어떻게 조치했나요 *                       │  │ 신고 내용               │
│ [부품 교체] [조정·재설정] [청소·이물 제거] │  │ 6층 남자 화장실 가장 …  │
│ [확인 결과 이상 없음] [임시 조치·후속 필요]│  │ 위치 6층 화장실 · 급배수 │
│ 메모 (선택)  [textarea, 1~2줄]           │  │ 첨부 사진 없음          │
│ 조치 사진 (선택)  [사진 첨부]  파일명 ×    │  │ 처리 이력 …             │
│                                          │  └─────────────────────────┘
│ [작업 완료]   반납                        │
└──────────────────────────────────────────┘
```

- 보조 열에 신고 내용·위치·첨부 사진·이력을 병기한다(WX-16). 헤더에는 제목·위치·번호만.
- **조치 내용 = 선택지 + 메모** (WX-18, P-H 기본안): 정형 조치 5개 중 하나 이상을 탭으로 고르면 필수가 충족된다. 메모는 선택. 저장 시 `resolution.content`에는 `선택지 라벨 — 메모` 형태로 합쳐 넣는다(API·ERD 변경 없음). 선택지 목록은 `constants.js`에 두고 관리소장 화면에서는 건드리지 않는다.
- **소요 시간 입력 제거** (WX-18, P-G 기본안): `durationMinutes = completedAt − assignedAt`을 `api.js completeComplaint`에서 자동 산출해 `resolution.durationMinutes`에 저장한다. 화면에서 입력받지 않는다. 신고자·관리소장 화면의 "소요 시간" 표시는 그대로 유지된다.
- `작업 완료`는 폼 하단 주 버튼. 비어 있어도 제출 시도는 가능하고 `조치 내용을 골라 주세요.`를 선택지 아래 표시(WX-17). 처리 중에는 버튼만 비활성.
- 조치 사진: 파일명 목록 + 개별 제거(WX-19). MOCK은 파일명만 저장한다.
- `반납`은 폼 하단 보조 행동. 헤더에서 뺀다.
- 작성 중 이탈: 선택·메모·사진 중 하나라도 있으면 `작성 중인 결과가 사라집니다` 확인 (`계속 작성` / `나가기`). 아무것도 없으면 확인 생략.
- 저장 실패(`409 NOT_ASSIGNEE` — 관리소장이 회수·재배정한 경우): `이 작업은 더 이상 내 담당이 아닙니다. 관리소장이 담당을 바꿨습니다.` + 내 작업으로 이동. 작성 내용은 즉시 지우지 않는다.

**E-04 반납 확인**

- 제목 `이 민원을 반납할까요?`, 설명 `지금 적던 내용은 저장되지 않습니다. 이 민원은 미배정 목록으로 돌아가 다른 기사가 맡을 수 있게 됩니다.`
- (P-A 채택 시) 선택 메모 `반납 사유 (선택)` → 이력 note.
- 버튼 `계속 하기` / `반납`. 초점은 `계속 하기`.
- "취소"라는 말은 쓰지 않는다 — 신고자의 민원 취소(`CANCELED`)와 혼동된다(12장 R-05).

### 6.5 공통 셸 (`StaffShell.vue`)
